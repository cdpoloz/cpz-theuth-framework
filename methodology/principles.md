# Principles

An initial proposal for designing a Theuth knowledge base; it should be tested against real cases.

1. **Save with a reason.** Capture an item if it helps remember, understand, decide, or continue work. Note why it matters and where it fits.
2. **Preserve provenance.** Record origin, author or entity, date, and a locatable reference: URL, document, conversation, or measurement. When a claim matters, link it to the specific passage that supports it.
3. **Separate evidence from interpretation.** Distinguish direct observations, claims attributed to sources, personal inferences, and adopted decisions. A synthesis or derived answer may guide retrieval, but does not by itself become independent evidence from the original source.
4. **Keep units manageable.** A note should have one central topic. Separate claims that can change or be retrieved independently.
5. **Make time visible.** Include creation, validity, and review dates when relevant. Do not silently overwrite earlier decisions.
6. **Update incrementally and explainably.** When a claim, synthesis, or decision changes, preserve what remains valid and record what changed, why, when, and on what evidence. Link versions or records when meaning or validity changes. Changes in form that do not alter meaning do not need a separate record.
7. **Distinguish present from history.** Maintain a current summary to guide present work. Use Git history and linked records to reconstruct changes; retain dated snapshots only when it is useful to preserve a milestone or retrievable checkpoint. None of these layers replaces sources or canonical records.
8. **Retrieve in layers.** For current status, start with the current project summary. Open decisions and sources when the query requires them; use a historical snapshot when asking about a past milestone.
9. **Treat summaries as maps.** The project file guides readers through the current state. Dated snapshots are optional historical checkpoints with scope and links to canonical records; they replace neither the current summary nor evidence.
10. **Keep derivatives traceable.** A synthesis, answer, or note created by an LLM is derived material: link it to its supporting sources and locators. Do not automatically treat it as an independent source or use an earlier synthesis as original evidence.
11. **Use portable formats.** Prefer plain text and predictable names. Git shows changes but does not explain their meaning on its own.
12. **Minimize and protect.** Save only what is necessary. Keep credentials and especially sensitive data out of the ordinary repository.
13. **Design around real queries.** Test whether the system can answer what is known, why, since when, and what has changed.

# Principios

Propuesta inicial para diseñar una base Theuth; debe contrastarse con casos reales.

1. **Guardar con una razón.** Captura una pieza si ayuda a recordar, comprender, decidir o continuar un trabajo. Anota por qué importa y dónde encaja.
2. **Conservar la procedencia.** Registra origen, autor o entidad, fecha y una referencia localizable: URL, documento, conversación o medición. Cuando una afirmación importe, enlázala con el pasaje concreto que la respalda.
3. **Separar evidencia e interpretación.** Distingue observaciones directas, afirmaciones atribuidas a fuentes, inferencias propias y decisiones adoptadas. Una síntesis o respuesta derivada puede orientar la consulta, pero no se convierte por sí sola en evidencia independiente de la fuente original.
4. **Mantener unidades manejables.** Una nota debe tener un tema central. Separa afirmaciones que puedan cambiar o consultarse independientemente.
5. **Hacer visible el tiempo.** Incluye fechas de creación, vigencia y revisión cuando sean relevantes. No sobrescribas silenciosamente decisiones anteriores.
6. **Actualizar de forma incremental y explicable.** Al cambiar una afirmación, síntesis o decisión, conserva lo que sigue siendo válido y registra qué cambió, por qué, cuándo y con qué evidencia. Usa enlaces entre versiones o registros cuando cambie su significado o vigencia. Las ediciones de forma que no alteren el sentido no requieren un registro separado.
7. **Distinguir presente e historia.** Mantén un resumen vigente para orientar el trabajo actual. Usa el historial de Git y los registros enlazados para reconstruir cambios; conserva snapshots fechados solo cuando convenga fijar un hito o checkpoint consultable. Ninguna de estas capas sustituye a las fuentes ni a los registros canónicos.
8. **Recuperar por capas.** Para el estado vigente, empieza por el resumen actual del proyecto. Abre decisiones y fuentes cuando la consulta lo requiera; usa un snapshot histórico si preguntas por un hito pasado.
9. **Tratar resúmenes como mapas.** El archivo de proyecto orienta sobre el estado actual. Los snapshots fechados son checkpoints históricos opcionales con alcance y enlaces a registros canónicos; no reemplazan ni el resumen vigente ni la evidencia.
10. **Mantener trazables los derivados.** Una síntesis, respuesta o nota creada por un LLM es material derivado: enlázala con las fuentes y localizadores que la respaldan. No la conviertas automáticamente en una fuente independiente ni uses una síntesis previa como evidencia original.
11. **Usar formatos portables.** Prioriza texto plano y nombres previsibles. Git muestra cambios, pero no explica por sí solo su significado.
12. **Minimizar y proteger.** Guarda solo lo necesario. Mantén credenciales y datos especialmente sensibles fuera del repositorio ordinario.
13. **Diseñar desde consultas reales.** Prueba si el sistema responde qué se sabe, por qué, desde cuándo y qué ha cambiado.
